# 复盘报告写作手册（给大模型 / 给写 prompt 的人）

报告最终是**发给客户**的。客户不关心 SQL，只关心三件事：
**我这周怎么样、哪里有问题、下周具体改什么。**

---

## 一、结构（固定 6 段，不要自由发挥）

```markdown
## 一、一句话结论      ← 2 句话以内，给老板看的
## 二、关键数据        ← 本期 vs 上期，直接引用事实包（系统会附详细表格，这里只写要点）
## 三、问题诊断        ← 按 critical → warn → info，只写事实包里有的诊断
## 四、内容侧优化动作   ← 3–5 条，每条 = 动作 + 改哪里 + 影响哪个指标
## 五、下周期执行清单   ← 排期：哪天做什么，目标是多少
## 六、数据说明与风险   ← 数据缺口、口径、结论可信度限制
```

**不要**加一级标题（系统会拼 `# 账号名 账号数据复盘`），不要用代码块包住正文，不要写"以下是报告"。

---

## 二、一句话结论怎么写

三种句式，按数据实际情况选：

| 情况 | 句式 |
| --- | --- |
| 有增长 | 「本期播放 X（环比 +Y%），{最强项}是主要拉动力，{最弱项}是下一阶段重点。」 |
| 持平/微降 | 「本期播放基本持平（环比 -Y%），但{结构性问题}依旧：{一句证据}。」 |
| 明显下滑 | 「本期播放环比 -Y%，主要是{原因线索}；{最该改的一件事}已在诊断中给出。」 |

判断依据只能是 `kpi.delta.plays_pct`、`funnel.finish_rate`、`funnel.engagement_rate`、
`kpi.current.followers_net` 这四个里的组合。**不要**引入其它数字。

---

## 三、优化动作库（按诊断 code 取用）

每条动作必须是「**改什么 + 怎么改 + 看哪个指标**」三件套。

### `PLAY_DROP` / 流量下滑
- 把上周期 TOP1 作品的**前 3 秒结构**抄成模板，本周新选题全部按这个开头写。
- 同一选题出 2 版：A 版结论前置、B 版悬念前置，只测开头，看 `cover_click_rate` 与 `finish_rate`。
- 避开与下滑期同时发布的同类选题，先换场景/换人群再试。

### `FINISH_RATE_LOW` / 完播率低
- 前 3 秒直接抛结论或冲突，删掉自我介绍与铺垫。
- 时长压到 15–30 秒；单条只讲一个点。
- 结尾砍掉"点赞关注"式自述，改成一句有信息量的话或直接收尾。

### `INTERACTION_LOW` / 互动率低
- 埋一个可代入的提问（"你们家是不是也这样？"），不要尬问。
- 评论区高赞问题直接变成下一条选题（内容来源于用户，互动自然高）。
- 结尾给"值得收藏"的理由（清单、预算表、避坑点），提升 `收藏率`。

### `FOLLOWER_STALL` / 涨粉停滞
- 用一句话说清"关注后能持续得到什么"（系列化内容最有效）。
- 检查是否发了与账号定位不符的内容（对比取关数与播放结构）。
- 把爆款做成"下一集预告"，用连续性拉动关注。

### `PUBLISH_GAP` / 断更
- 库存素材优先补位，先恢复节奏再谈优化。
- 定一个可持续的节奏（建议每周 3 条）而不是"每天更"。

### `CONCENTRATION_RISK` / 依赖单条爆款
- 把爆款拆成公式：钩子类型、结构、话术、卖点位置，各写一行。
- 用 3–5 条内容验证同一公式在不同场景下是否可复制。
- 若不可复制，说明是撞热点，立刻安排第二条选题对冲。

### `OLD_CONTENT_DRIVEN` / 增量靠老作品
- 老作品的长尾说明选题有需求，把它的**评论区需求**整理成 10 条新选题。
- 在新内容里做"系列第 N 集"，把老作品的流量导给新内容。

### `NO_NEW_PUBLISH` / 停更
- 明确给出"本周必须发的 3 条"，写清选题与开头。

## 四、反面例子（评委级挑错）

| 反面写法 | 问题 | 改法 |
| --- | --- | --- |
| "整体表现良好，继续保持" | 没有信息量，客户感觉被敷衍 | 给出具体数字与下一步动作 |
| "完播率偏低，建议优化内容" | 不可执行 | "完播率 18.8% 低于健康线 25%：把结论前置到 3 秒，时长压到 25 秒以内" |
| "建议多做爆款" | 空话 | "复刻 TOP1 的钩子结构，本周拍 3 条同结构不同场景的内容" |
| 列出 10 条建议 | 客户不执行 | 最多 5 条，按影响 × 成本排序 |
| 把每个数字都念一遍 | 客户看不下去 | 只讲结论性数字，细节放附表 |

## 五、prompt 使用说明（handoff 模式）

`dyreview review` 产出的 `prompt` 由两部分拼成：

```
<系统提示：角色 + 7 条硬规则 + 输出结构>
---
<用户提示：报告对象 / 已算好的数据 / 完整事实包 JSON / 规则引擎诊断 / 数据缺口>
```

对接 Crabot 时的建议：

1. **原样传入**，不要自己精简事实包——精简掉的部分往往正是模型需要引用的证据；
2. 模型返回后**必须走 `render`**，不要直接把模型输出推给客户（数字校验是最后一道闸门）；
3. 如果 `render` 报 `NUMBERS_INVALID`：把 `validation.violations` 和事实包一起再喂一次，
   明确要求"只使用事实包中的数字"，**最多重试 1 次**（`skill.max_llm_rounds=2`）；
4. 记录 token：把模型返回的 `usage.prompt_tokens` / `completion_tokens` 通过
   `render --input-tokens/--output-tokens` 传进来，会写进 `dy.llm_usage`；
5. `llm.mode=handoff` 时 Skill 不需要大模型密钥，用哪个模型由 Crabot 决定（成本可控）。

### 温度与长度

- `temperature=0.3`：报告要稳定，不要发散；
- `max_output_tokens=3000`：正文 900–1400 字，加上附表卡片通常 2–3 屏；
- 事实包已做瘦身（去掉数字白名单、TOP 列表截到 5 条），prompt 一般 4–8KB。
