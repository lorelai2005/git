# 爆款逻辑库

文件：`knowledge/viral-logic/library.json`
调用：`python scripts/retrieve.py logic --query "<目标词>" --count 5`

库里的东西是**结构资产**，不是文案素材。它回答的问题是：
「这条片子应该按什么顺序讲，每段时间留给什么，首句用什么公式，拍摄时不能违反什么。」

---

## 一张卡包含什么

```json
{
  "id": "LOCAL-LANDMARK-OPENING",
  "name": "同城地标锚定 · 开店结果前置",
  "family": "开业通知",
  "goal_types": ["开业", "同城到店", "新店冷启动"],
  "audience_fit": ["本地 25—40 岁女性", "同城新客"],
  "duration_range": [55, 70],
  "beats": [{"t": "0—3秒", "role": "结果前置", "desc": "…"}],
  "hook_formula": "{地标}{人群}，{品牌}{动作状态}了，{锚点描述}就能找到。",
  "voice_rules": ["…"],
  "shoot_rules": ["…"],
  "risks": ["…"],
  "tags": ["同城", "开业", "地标"],
  "evidence": "淑情哲依 01「同城开店通知」"
}
```

| 字段 | 作用 | 写不好会怎样 |
| --- | --- | --- |
| `id` | 唯一标识，`大写-连字符` | 引用断了，脚本回溯不了 |
| `goal_types` | 目标匹配，检索权重 2 | 目标词检索不到这张卡 |
| `audience_fit` | 人群匹配，检索权重 2 | 被推给不合适的客户 |
| `duration_range` | 建议时长区间，写稿时约束总长 | 30 秒的片子被套了 60 秒的骨架 |
| `beats` | **核心**：时间段 + 该段职能 + 写法 | 写稿没骨架，只能凭感觉 |
| `hook_formula` | 首句公式，`{}` 是待填槽位 | 每条片子首句都从零想 |
| `voice_rules` | 口播层面的禁令 | 出现无法核实的表达 |
| `shoot_rules` | 拍摄层面的禁令 | 拍了等于白拍的画面 |
| `risks` | 这条结构特有的坑 | 同一个坑反复踩 |
| `tags` | 检索权重最高（3） | 命中率低 |
| `evidence` | 来源出处：哪个客户哪条片子验证过 | 无法判断这张卡是否靠谱 |

`beats` 的时间段必须**首尾相接且从 0 开始**，和最终脚本的时间轴一致，
这样写稿时直接照着抄时间列，不会出现断档。

## 检索怎么打分

`retrieve.py` 是可解释的加权匹配，不用向量库（结构化内容用关键词更可控）：

| 命中位置 | 权重 |
| --- | --- |
| `tags` | ×3 |
| `goal_types` | ×2 |
| `audience_fit` | ×2 |
| `name` / `hook_formula` / `beats[].desc` / `risks` 的 2-gram | ×1 |

返回里每条都带 `score` 和 `why`（命中了哪些标签/目标/正文词）。
**`why` 是给你判断的，不是给客户看的**：如果命中的都是泛词（「到店」「风格」），
分数高也可能不合适，回头看 `beats` 是否真的对得上本次目标。

`--query` 的写法：用 2—4 个名词短语，不要整句话。

- 好：`开业 同城到店 福利`
- 差：`帮我写几条开业的时候用的抖音视频脚本`

## 什么时候加卡

满足任一条就加：

1. 对标拆解里连续 2 条以上 `logic_id` 都对不上已有卡
2. 客户行业换了，现有卡的 `beats` 结构明显不适用（例：餐饮排队的结构 ≠ 服装试穿的结构）
3. 某张卡在自己客户身上跑出了显著高于均值的完播/到店，值得固化成模板

加卡时**必须写满** `beats`（时间+职能+写法）、`hook_formula`、`voice_rules`、
`shoot_rules`、`risks`、`evidence` 六项，缺任意一项都不要合进库——
半张卡会让写稿时凭感觉补，等于没有。

## 现有卡一览

| id | 名称 | 适用 |
| --- | --- | --- |
| `LOCAL-LANDMARK-OPENING` | 同城地标锚定 · 开店结果前置 | 开业、新店冷启动、同城到店 |
| `BENEFIT-BREAKDOWN` | 福利清单拆解 · 条件透明 | 开业福利、活动引流 |
| `PAIN-FREE-SERVICE` | 痛点直呼 · 免费服务承诺 | 服务种草、降低决策门槛 |
| `A/B-STYLE-CONTRAST` | 二选一风格对比 · 自我对号入座 | 风格教育、货品导览、提升试穿率 |
| `FOUNDER-ORIGIN-STORY` | 主理人身份故事 · 真实经营证明 | 品牌信任、主理人 IP |
| `STORE-WALKTHROUGH-POV` | 第一视角探店动线 | 探店、空间展示 |
| `PRICE-ANCHOR-COMPARE` | 价格锚点对比 · 同款差价 | 价格说服、性价比 |
| `BEFORE-AFTER-PROOF` | 改造前后对比 · 效果自证 | 服务效果、试穿转化 |
| `LISTICLE-SAVE-BAIT` | 清单体 · 值得收藏的 N 个理由 | 收藏率、信息密度 |
| `QUESTION-DIAGNOSIS` | 3 秒自测题 · 对号入座 | 完播率、人群筛选 |

前 5 张来自参考稿 5 条实拍验证脚本；后 5 张是同类目常用结构，
`evidence` 里标注了「未用本例实拍验证」，使用时要更保守。

## 一单 5 条怎么排

不要 5 条都用最强的卡。参考稿的排法是**一条卡对一种决策阶段**：

| 位置 | 卡 | 决策阶段 |
| --- | --- | --- |
| 01 | 同城地标锚定 | 还不知道你存在 |
| 02 | 福利清单拆解 | 知道了，在算值不值得来 |
| 03 | 痛点 + 免费服务 | 有需求但怕麻烦/怕被推销 |
| 04 | 二选一风格对比 | 想买但选不出来 |
| 05 | 主理人故事 | 需要信任，才愿意专门跑一趟 |

照这个顺序排，5 条片子会互相补位；如果 5 条都在讲福利，第 3 条之后就开始掉。
