# 质量闸门

两道闸：**自动校验**（`validate.py`，build 时自动跑）+ **人工复核**（逐页 PNG）。
自动的管「会不会出错」，人工的管「好不好看、能不能拍」。

---

## 自动校验项

```bash
python scripts/validate.py <payload.json> --client <id>
```

`errors` 阻断出片，`warnings` 只提示，`notes` 是待确认提醒。

### S 结构

| code | 判据 | 为什么 |
| --- | --- | --- |
| `S1` | `meta` 五个字段齐全 | 少一个，拍摄组就不知道这条片子的共同目标 |
| `S2` | 至少一条脚本 | — |
| `S3` | 每条脚本 7 个字段齐全 | 少「内容结构」就没法审稿，少「开头钩子」就没法剪 |
| `S4` | 表格每行四列非空 | 空「执行要点」等于这行没人负责 |
| `S5` | `执行要点` ≥ 8 字（warning） | 「注意细节」这种等于没写 |

### H 钩子

| code | 判据 |
| --- | --- |
| `H2` | 钩子是口播首段的压缩版（重合 60%—99%）→ warning |
| `H1` | 钩子与口播首段重合 < 60% → error |

参考稿 01 的钩子和首段并不是逐字相同：
钩子是「…3 号门斜对面就能找到」，首段是「…位置就在菱角湖万达 3 号门斜对面」。
这是**正确做法**：口播要能自然念出来，字幕要短。
所以判据是「语义一致 + 高度重合」，不是「逐字相等」。

### T 时间轴

| code | 判据 |
| --- | --- |
| `T1` | 时间格式能解析（`0—3秒` / `3—15秒`） |
| `T2` | 结束 > 开始 |
| `T3` | 第一行从 0 秒开始 |
| `T4` | 上一行结束 = 下一行开始（不允许断档或重叠） |

时间轴断档是最常见的隐性错误：后期照着表格铺素材时，会发现中间少了 5 秒，只能瞎补。

### F 事实（最重要）

| code | 判据 |
| --- | --- |
| `F1` | 文案里出现的**每个数字**，都要能在 `profile.json` 的 `facts`（`status == confirmed`）里找到 |

检查范围：`structure` + `hook` + `voiceover` + 表格的 `picture` / `audio` / `note`
（`time` 列的数字是时间码，自动排除）。

命中 `F1` 只有两条路：**去确认事实**，或者**改掉文案**。没有第三条。
这条规则是为了把「编一个数字」这件事变得麻烦到不值得做。

### C 合规

| code | 判据 |
| --- | --- |
| `C1` | 命中绝对化用语或客户禁用语 |
| `C2` | `unified_facts` 里包含客户禁用表达（warning） |

内置绝对化词表：最好 / 最佳 / 最低 / 最高 / 最强 / 全网最 / 第一 / 唯一 / 顶级 /
国家级 / 世界级 / 绝无仅有 / 100% / 百分百 / 保证 / 绝对 / 永久 / 根治 / 秒杀全网。

「第一」「最好」走上下文正则，不误伤「第一种风格」「我最想做的事情」。
客户专属禁语在 `profile.json` 的 `banned_claims` 与 `tone.avoid` 里加。

### L 口播长度

按 **5 字/秒** 估算（普通话口播的常用速率），与时间轴总长比较：

| code | 判据 |
| --- | --- |
| `L1` | 估算时长与时间轴偏差 > 35%（warning） |
| `L2` | 单条 < 25 秒或 > 90 秒（warning） |
| `L3` | 存在 < 8 字的口播段（warning） |

偏差大通常是两种问题：口播写太满（拍摄时念不完，只能加速或砍词），
或者时间轴留太长（剪出来节奏散）。

### G 标签

| code | 判据 |
| --- | --- |
| `G1` | 少于 3 个（warning） |
| `G2` | 有标签不以 `#` 开头（error） |
| `G3` | 未包含品牌词（error） |

### D 账号逻辑去重

| code | 判据 |
| --- | --- |
| `D1` | 本次任务有真实 `account_id`，且与客户和目标绑定 |
| `D2` | 每个候选逻辑都调用 `check_account_logic_duplicates` 检查 `account_logic_usage` |
| `D3` | 同账号命中 `usage_status IN ('used', 'candidate')` 的逻辑或内容签名时，不能出片 |
| `D4` | 成功出片后，本次 `logic_signature` 和内容签名已写回使用记录；没有写回路径时必须标记闭环未完成 |

`rejected` 和 `archived` 记录不阻断复用。去重检查只针对同一 `client_id + account_id`，不能把一个账号的历史使用误当成所有账号都不能用。

### P 待确认

`P1`：客户 `pending` 里还有未确认项时提醒，并列出来。
这不是错误——但交付时必须告诉客户「这几项没写死」。

## 人工复核（出片后必做）

build 完成会打印 `逐页图：` 路径，逐页看图，按下面清单过：

### 版式

- [ ] 主标题在**一行**内（折行会破坏整页重心）
- [ ] 主标题下横线与文字不贴、不远离（约 3.7 mm）
- [ ] 小标题竖条高度约 12 mm，上下都超出文字（这是参考稿最显眼的特征）
- [ ] 表格没有被拦腰截断；跨页时首行不是孤立的半行
- [ ] 表格右边缘与正文右边缘对齐
- [ ] 没有一条正文段落被挤到下一页孤零零一行（`keep_with_next` 只在标题上生效，段落要靠字数调）

### 内容

- [ ] 5 条脚本的开头三秒各不相同（都是「大家好我是…」就重写）
- [ ] 每条脚本的 `structure` 和 `shoot` 时间轴对得上（结构上有 5 步，表格只有 3 段 → 有问题）
- [ ] 口播念一遍，能不能一口气念完一段（念不完就拆段）
- [ ] `执行要点` 每行都有「必须」或「禁止」（全是正面要求 → 说明没找到风险）
- [ ] 最后「统一发布前核对」写的是这一单特有的坑，不是通用检查项

### 交付话术

出片后至少说明三件事：

1. 用了哪几张爆款逻辑卡（对应关系列出来）
2. 哪几条信息还是待客户确认的（`P1` 列出来的）
3. 拍摄前需要准备什么（道具、出镜人员、授权）

## 出片失败怎么办

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Word 导出 PDF 失败` | Word 未安装 / COM 被占用 / 文件被占用 | 关掉已打开的 docx，重跑；确认本机装了 Word |
| PDF 页数比预期多 | 口播太长或段落间有空行 | 压缩口播，删空行 |
| 表格单元格里文字跳行很怪 | 列宽被自适应改掉了 | 确认 `build_docx.py` 的 `COL_RATIO` 没被动过 |
| 中文变成宋体/方块 | 字体缺失 | 确认系统有微软雅黑（`C:\Windows\Fonts\msyh.ttc`） |
| 竖条只有文字高 | 小标题行距被改小了 | 行距必须 32 pt，见 `references/script-format.md` |
