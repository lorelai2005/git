# 数据库改动记录与原因（renwei v1.0 → v1.2）

> 对象：193 服务器 `dtk5-postgres-1` 上的新库 `renwei`（`core` / `ops` / `mdl` 三 schema）
> 时间：2026-11-06
> 现状态：**34 表 / 8 视图 / 135 索引 / 78 CHECK / 68 外键 / 24 触发器**，生产流量已从旧库 `renwei_script` 切过来
> 本文只记「改了什么」和「为什么改」，不重复 DDL 细节（DDL 见 `deploy/01_schema.sql`）

---

## 一、变更总览

| 阶段 | 时间 | 改了什么 | 起因 |
|---|---|---|---|
| 旧库现状 | 2026-10 及以前 | `renwei_script` 单库：`public` 13 表 + `dy` 13 表 + `review` 23 表 | 早期边做边加 |
| **v1.0 结构** | 2026-11-06 | 新建 `renwei` 库，拆成 `core` 8 表 + `ops` 13 表 + `mdl` 13 表 | 你提出两类业务（长期运营 / 活动运营）要分库，且都走七层链 |
| **v1.1 复用** | 2026-11-06 | 加 `max_reuse_per_campaign`、`reuse_seq`、配额触发器、复用看板 | 你说：活动逻辑可以同活动复用，但不超过 3 次 |
| **v1.2 上线** | 2026-11-06 | 数据迁移、19 个工具改造、切库、入库四道保险 | 你说：三步全做完，并保证每次视频都入库 |
| **v1.3 口径定版** | 2026-11-06 | 七大模型「图片中的方向 / 统一名称 / 作用」定版 + `definition_ver` + 字典视图 | 你给了七大模型统一定义表，要求放进数据库 |

## 二、逐项改动与原因

### C1 · 从「一个库一堆表」改成「core + ops + mdl 三层」

**改了什么**：新建库 `renwei`，把原来混在 `public` 里的表按职责拆成三层 —— `core`（客户/账号/资料/事实/视频主档/收件/交付/审计，8 表）、`ops`（长期运营，13 表）、`mdl`（活动模型，13 表）。

**为什么**：你给了两类业务 ——「给门店工厂做长期短视频运营」和「活动短视频运营」，并且明确要求**两种模式都要走「客户 → 事实 → 对标 → 逻辑 → 目标 → 出片 → 去重写回」**。旧库的表是按功能零散堆的，表达不了"同一套链条两种走法"。

**影响**：两个库不是复制粘贴，中间两层结构完全不同（见 C4 / C5）。

**验证**：34 表 / 7 视图建成，冒烟测试走完完整七层链路，回滚零残留。

---

### C2 · 客户和事实「共享一份」，不做双份

**改了什么**：`core.clients` / `core.accounts` / `core.source_documents` / `core.fact_items` 两个库共用，不各存一份。`fact_items` 加 `scope`（`ops` / `campaign` / `both`）区分适用面。

**为什么**：同一个客户（东海文峰）既有长期运营又有开仓活动，各存一份客户和事实**必然口径漂移**；而且 PostgreSQL **跨 database 建不了外键**，事实和脚本之间的引用会断。真要物理双库，就得双写 + 定时对账，代价远大于收益。

**影响**：方案是「1 个 database，3 个 schema」——对外是你说的两个库，对内客户和事实只存一份。

---

### C3 · 对标视频：一条主档 + 按模式分流

**改了什么**：
- `core.benchmark_videos`：只存「视频是什么」，按「平台 + 作品ID」全局唯一
- `core.benchmark_intake`：**收件箱**，记录渠道、原话、作品ID、判定模式（`ops`/`campaign`/`both`/`unknown`）、判定依据、路由人
- `mdl.benchmark_breakdowns`（模型视角）与 `ops.benchmark_breakdowns`（运营视角）**各自独立**

**为什么**：你的原话是「**每一次用户发的对标视频仁维 agent 都要存入相对应的数据库**」。旧库是「一条视频一张拆解卡」，没有"这条视频属于哪种运营"的概念。

**关键取舍**：同一条视频可能既值得长期运营借鉴、又值得活动借鉴，强行二选一必然丢信息 → 允许 `both`，两条链各拆一次；**`unknown` 也照样入库**，不静默丢弃。

**验证**：21 条视频全部有收件记录（含 FR-007 重复提交的 `rejected` 留痕）。

---

### C4 · 活动库的粒度从「整张逻辑卡」降到「槽位」

**改了什么**：新增 `mdl.model_slots`（7 模型 × 6 槽 = 42 行，槽位为 `hook` / `callout` / `conflict` / `proof` / `transition` / `cta`，每槽带 `intent` / `success_criteria` / `forbid`）；`mdl.scripts` 加 `slot_payload`（逐槽实稿）。

**为什么**：旧库 `logic_patterns` 的最小单位是一整张卡，导致「钩子很好但收口很弱」这种问题**没法单独替换**。活动运营真正可复用的资产是"结构件"，不是"范文"。

**影响**：有了 `slot_payload` 才能统计「M4 的 proof 槽在 12 条历史稿里平均分最低」，从而定向补素材；没有它，模型库只是一堆范文。

---

### C5 · 长期运营补三张关键表：人设 / 内容线 / 排期

**改了什么**：新增 `ops.personas`、`ops.content_series`、`ops.content_calendar`（旧库完全没有这三样，全是 0 条）。

**为什么**：长期运营不是「一次写 N 条」，是「维持一个号持续产出」。没有内容线，一个号写出来的脚本就是一堆彼此无关的单条；没有排期，「下个月发什么」每次都要重新想；没有人设，同一个号会写出四个人。

**影响**：`ops.scripts` 强制挂 `series_code` + `persona_code`；建议每个活跃账号 3–5 条内容线（少于 3 条必重复）。

---

### C6 · 枚举全部落成 CHECK，不再自由文本

**改了什么**：`verify_status`、`usage_status`、`fact_type`、`permission_status`、`material_status`、`evidence_status`、`detected_mode` 等 78 个 CHECK 约束。

**为什么**：诊断旧库时发现 `verify_status` 里塞的是「已读5/15页；ASR未人工听校」这种自由文本。**直接后果**：旧库两个统计视图用 `verify_status <> 'pending'` 判"已核验"，而所有值都不等于 `pending`，于是 `verified_count` 恒等于 `video_count` —— 视图完全失效。

**验证**：往 `verify_status` 插自由文本会被 CHECK 直接拒绝（已测）。

---

### C7 · 金句 `pass_all` 必须由分数支撑

**改了什么**：两个库的 `copy_gems` 都加约束：
```sql
check (not pass_all or (score_aliveness >= 60 and score_empathy >= 60 and score_infectiousness >= 60))
```

**为什么**：旧库 59 条金句**全部** `pass_all = true`、`veto_flags` 全是空数组。三维分数齐但只起记录作用、不参与筛选——「金句库」实质退化成一个手写句子列表。这条 CHECK 让"批量置 true"做不到。

**验证**：插 `pass_all=true` 但三维分只有 30 的数据，被 `ck_mdl_gems_pass_all` 拦下（已测）。

---

### C8 · 活动逻辑：同活动可复用，硬上限 3 次（v1.1，你直接指定的规则）

**改了什么**：
- `mdl.model_patterns.max_reuse_per_campaign` smallint 默认 3，`CHECK between 1 and 3`
- `mdl.script_usage.reuse_seq` smallint，`CHECK between 1 and 3`，触发器自动排 1→2→3
- 唯一键从「同活动禁重复」改成 `(campaign_id, logic_signature, reuse_seq) WHERE status IN ('used','candidate')`
- 触发器 `mdl.enforce_reuse_limit()` 拦第 4 次，报 `REUSE_LIMIT_EXCEEDED`
- 看板 `mdl.v_campaign_logic_reuse`（已用 / 上限 / 剩余）

**为什么**：你的原话「**活动运营的逻辑可以同活动复用，但是频率不要超过 3 次**」。我最初的设计是「同活动严禁重复」（唯一键直接锁死），等于一次都不许复用——**这条设计被你的规则推翻并替换**。

**影响**：`rejected` / `archived` 不占额度，改判后可再用一次；跨活动重新从 1 计数。

**验证**：同活动连用 3 次成功（seq 1/2/3）→ 第 4 次被拦 → 换活动重新从 1 开始 → 把第 3 条改 `rejected` 后能再用一次 → 想把上限改成 4 被 CHECK 拦。

---

### C9 · 活动逻辑可被长期运营复用

**改了什么**：`ops.logic_cards` 加 `source_mode`（`ops` / `campaign`）和 `model_pattern_id`（外键指向 `mdl.model_patterns`）。

**为什么**：你说「活动运营的逻辑可以复用」——复用不只在活动之间，一套活动打法沉淀下来，长期运营同样能用。留这条外键，运营侧复用时可回溯到源模型卡，而不是变成一张无出处的拷贝。

---

### C10 · 「每次视频都要入库」做成四道保险（v1.2，你直接指定）

**改了什么**：

| # | 机制 | 类型 |
|---|---|---|
| 1 | `route_benchmark` 作为唯一入库入口；`ingest_benchmark_breakdown` 查不到收件记录**直接拒绝** | 应用层 |
| 2 | 旧工具 `ingest_video_logic`、CLI `benchmark-ingest.js` 发现视频不在库，**自动补入库** | 兼容层 |
| 3 | `benchmark_videos` 上 `AFTER INSERT` 触发器，缺收件记录自动补建一条 | 数据库 |
| 4 | `v_video_intake_coverage`（无收件视频数，必须恒为 0）、`v_intake_pending`（有链接未落库，必须清空） | 校验视图 |

**为什么**：你的原话「**要保证每次视频都要入库**」。只靠 SKILL 写一句"请入库"不叫保证——模型会忘、老技能还在调旧工具名、也可能有人绕过工具直接写表。

**验证**：拿一个从未出现过的作品 ID 调旧工具 `ingest_video_logic`，自动产生 1 视频 + 1 收件 + 1 逻辑卡；当前 `no_intake = 0`、`pending_intake = 0`。

---

### C11 · 复盘层延期（你决定单独排）

**改了什么**：**没改**。`dy.*`（13 表）与 `review.*`（23 表，`metric_snapshot` 4368 条）仍在旧库 `renwei_script`，本次不迁。

**为什么**：你的原话「**复盘层单独排**」。技术上它也不该混着做 —— 不是"搬表"，是"把一条正在跑的采集管道换库"（写入方是 `renwei-review` + `renwei-douyin-collector` 两个独立容器，`metric_snapshot` 持续写入，迁移窗口的增量会丢，必须靠 `sync_cursor` 补采）。

**影响**：`list_client_accounts` 的作品数/指标数暂时返回 0，工具里已显式提示"不据此判断没数据"。预案见 `复盘层迁移预案.md`。

---

### C12 · 七大模型统一口径定版（v1.3）

**改了什么**：`mdl.activity_models` 的七个字段按业务方给出的定义表定版 —— `direction` = 图片中的方向、`name` = 统一模型名称、`purpose` = 作用；新增 `definition_ver`（当前 `1.0`，改定义必须升版本）；三个字段写死注释说明口径；新增字典视图 `mdl.v_model_definitions`。

**为什么**：模型名称是最容易漂移的东西 —— 参考图里写"热点话题"，策划嘴里叫"宠粉福利会"，代码里写 M2，三种说法指向同一个东西。把「图片中的方向」和「统一名称」分成两列存，是把**映射关系固化**，不是重复存名字。

**实测结果**：七条的定义文本与你给的表**完全一致**（说明此前从旧库 `model_categories` 迁移时口径没跑偏）。所以本次没有改数据，做的是**定版与固化**：加版本列、写死字段注释、建可查询的字典视图。

**表结构侧的影响**：
- 新增列 `definition_ver`（默认 `1.0`）—— 以后谁改定义不升版本，能查出来
- `is_active` 补注释：它是**素材可用性**标记，不代表模型是否存在。M6 因无素材仍为 `false`

**验证**：`select * from mdl.v_model_definitions` 返回 7 行，槽位均为 6，覆盖数反映真实素材量（M4 最强：8 张拆解卡 / 30 条金句；M6 为 0/0）。

## 三、被推翻 / 修正的设计（包括我写错的地方）

| # | 原设计 | 改成 | 原因 |
|---|---|---|---|
| R1 | 同活动**严禁**重复用同一逻辑，唯一键 `(账号, 活动, 签名)` | `(活动, 签名, 复用序号 1..3)` | 你的新规则：可复用但不超过 3 次 |
| R2 | `mdl.script_usage.campaign_id` **NOT NULL** | 允许为空 | 迁移时发现历史 78 条使用记录**没有活动概念**，强制非空只能造假数据 |
| R3 | 逻辑卡靠 `benchmark_video_id` 关联视频 | 改用 `content_id`（作品ID）回接 | 旧库 64/64 条的 `benchmark_video_id` **全部悬空**，指向不存在的视频 |
| R4 | 收件箱靠 `NOT EXISTS` 守卫防重复插入 | 外层表加别名 | 守卫里的 `id` 被内层 `benchmark_intake.id` 遮蔽，导致重跑多插 21 条；已修复并去重 |
| R5 | 视图由 `dtk` 创建后就完事 | 补 `grant` 给 `renwei_app` | 迁移建的 2 个视图 owner 是 `dtk`，业务账号读不到（冒烟时暴露） |

## 四、当前库全貌（每张表为什么存在）

### `core` 公共层 8 表 + 2 视图
| 对象 | 存在理由 |
|---|---|
| `clients` | 客户档案，所有数据的归属根 |
| `accounts` | 客户名下平台账号，脚本按号产出；也是脚本层与复盘层的接缝 |
| `source_documents` | 原始资料登记，按内容指纹去重 |
| `fact_items` | 事实库，脚本里"说什么"的唯一合法来源（`fact_type`+`permission_status`+`usable_for_script` 三重把关） |
| `benchmark_videos` | 对标视频主档，只存"视频是什么"，按作品ID全局唯一 |
| `benchmark_intake` | 收件箱与模式路由，**保证每条视频有去处**（C3/C10） |
| `deliverables` | 交付物台账（旧库缺失：出片只落文件系统，库里查不到交付过什么） |
| `agent_retrieval_logs` | 审计，加 `mode` 以区分两种运营 |
| `v_video_intake_coverage` / `v_intake_pending` | 入库保证的机检口径（C10） |

### `ops` 长期运营库 13 表 + 2 视图
| 对象 | 存在理由 |
|---|---|
| `benchmark_accounts` | 长期运营对标的是**账号**，不是单条视频（样本 <3 不许下账号级结论） |
| `benchmark_breakdowns` / `segments` / `evidence` | 运营视角拆解：归到哪条内容线、哪些动作能每周照做 |
| `personas` | 人设设定（C5） |
| `content_series` | 内容线/栏目 —— 长期运营的骨架（C5） |
| `content_calendar` | 排期与库存水位（C5） |
| `logic_cards` | 账号级/系列级/单条级三种粒度的打法（C9 支持复用活动卡） |
| `copy_gems` | 按内容线×人设归类的金句（C7 约束） |
| `script_goals` | 阶段目标（周/月/季），必须覆盖哪几条线 |
| `scripts` / `script_versions` | 脚本正文与版本，强制挂内容线+人设 |
| `script_usage` | 去重账本：账号 × 内容线 × 签名 × 时间窗 |
| `v_series_coverage` / `v_calendar_backlog` | 内容线覆盖度 / 防断更 |

### `mdl` 活动模型库 13 表 + 3 视图
| 对象 | 存在理由 |
|---|---|
| `activity_models` | M1–M7 模型类目：编号 / 图片中的方向 / 统一名称 / 作用，带"写成什么样就废了"（`death_trap`）；口径版本见 `definition_ver`（C12） |
| `model_slots` | 42 个槽位，**模型库的真正颗粒**（C4） |
| `model_patterns` | 模型组合卡 = 活动逻辑层，默认跨活动可复用（C8 的上限就挂在这张表上） |
| `copy_gems` | 按模型×槽位归类的金句，检索能精确到"M4 的 proof 槽有哪些原话" |
| `benchmark_breakdowns` / `segments` / `evidence` | 模型视角拆解，一条视频可出多个模型卡 |
| `campaigns` / `campaign_kpis` | 活动主档与指标，把"脚本 → 结果"接上 |
| `campaign_goals` | 本次脚本目标：几条、必须覆盖哪些模型、发布窗口 |
| `scripts` / `script_versions` | 脚本正文，含 `slot_payload` 逐槽实稿 |
| `script_usage` | 去重账本：活动 × 签名 × 复用序号（C8） |
| `v_model_slot_coverage` / `v_campaign_readiness` / `v_campaign_logic_reuse` / `v_model_definitions` | 槽位覆盖度 / 活动开工就绪度 / 复用额度 / 七大模型统一定义字典 |
