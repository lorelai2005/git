# 任务三 · 账号数据复盘工作流 — 技术方案

> 版本：v1.0　|　对应母文档：《仁维 Agent 三大工作流任务文档 v1.0》第四章
> 范围：Crabot Agent 平台「账号数据复盘 Skill」的授权、采集、存储、分析、交付全链路
> 状态：待评审

---

## 0. 一句话结论

**目标可实现，但必须把母文档 4.2 第 1 步的「Agent 保持和客户账号后台的长期连接」改写为「一次授权 + 定时拉取 + 落库 + Skill 只读分析」。**

Agent 平台没有常驻进程，客户后台也没有可长连的协议；「长期」的正确载体是**长期有效的 OAuth 授权关系**，不是长期会话。

## 1. 背景与目标

### 1.1 业务目标

仁维作为代运营方，需要对自己服务的客户账号做**周期性数据复盘**，输出可落地的提升方案，替代目前人工每周登录各平台后台截图、导表、写报告的流程。

### 1.2 可量化的成功标准

| 维度 | 现状（假设） | 目标 |
|---|---|---|
| 单账号周报耗时 | 40–60 分钟 | < 5 分钟（人工只做审校） |
| 数据获取方式 | 人工登录后台导出 | 自动采集，延迟 < 6 小时 |
| 报告一致性 | 依赖个人经验 | 统一诊断规则 + 统一报告模板 |
| 授权维护 | 每次都要客户给验证码 | 一次扫码，滚动续期，失效自动告警 |

### 1.3 本文档不覆盖

- 任务一（脚本生成）与任务二（视频粗剪）的库表与 Skill
- 客户端投放/广告数据（巨量引擎、聚光平台）——后续可作为独立数据源接入，接口预留
- 竞品第三方数据商的商务采购

## 2. 需求边界：做什么 / 不做什么

### 2.1 做（In Scope）

1. 客户账号的 OAuth 授权接入与长期维护（多平台、多账号）
2. 定时采集账号级与作品级指标，落 MySQL
3. 指标口径统一（平台原始字段 → 内部标准 metric_code）
4. 复盘 Skill：读库 → 诊断 → 生成报告 → 飞书回推
5. 授权失效 / 采集失败的告警与自助恢复引导
6. Token 消耗统计（对齐母文档第五章公共约束）

### 2.2 不做（Out of Scope，且永不建议做）

| 不做 | 原因 |
|---|---|
| 云端集中托管客户 cookie / session | 违反平台协议、封号风险、合规事故 |
| 逆向创作者中心私有接口 | 违反开发者协议，触《数据安全法》《个人信息保护法》，量大涉刑 |
| 让客户交账号密码代登录 | 无法审计、无法止损 |
| 实时（分钟级）数据 | 复盘是周期性业务，分钟级无价值且触发限流 |

### 2.3 关键设计原则

- **P1 采集与分析解耦**：采集是常驻服务的事，Skill 只读库。Skill 超时或平台抖动不影响已有数据。
- **P2 凭证最小化**：只在授权层持有 refresh_token，全链路加密，任何日志不得出现明文。
- **P3 口径先行**：先定 metric_dict，再写 adapter。反过来一定返工。
- **P4 幂等与可重放**：同一账号同一天重复采集不产生脏数据，可随时按日期重跑。
- **P5 降级可用**：官方 API 拿不到的字段，用「第三方数据商 / 客户手动补录 / 留空并标注」三选一，绝不用非合规手段补。

### 3.1 为什么采集服务必须独立部署

| 约束 | 后果 |
|---|---|
| Crabot 会话级生命周期，无常驻进程 | 无法跑定时任务 |
| Skill 单次执行有超时（待确认，通常 30–120s） | 拉不了多账号批量数据 |
| 平台 API 有 QPS 与日配额 | 需要错峰、退避、重试，长耗时 |

**若 Crabot 后续支持定时触发 + 长任务，采集服务可降级为「被 Skill 调用的一次性拉取器」，架构不变，只是部署位置变化。**

## 4. 授权层设计

### 4.1 授权流程（以抖音为例，其他平台同构）

```
运营同学 在飞书发："授权新账号 客户A 抖音"
   → Skill 调 auth-service 创建授权会话，返回一次性链接
   → 运营转发给客户，客户在手机上点开 → 抖音授权页 → 确认
   → 平台回调 auth-service /oauth/callback?code=...
   → 换取 access_token + refresh_token + open_id
   → refresh_token 用 AES-256-GCM 加密入库
   → 回推飞书："客户A 抖音账号已授权，有效期至 2026-xx-xx"
```

### 4.2 Token 生命周期管理

| 项 | 策略 |
|---|---|
| access_token | 内存/Redis 缓存，过期前 5 分钟刷新 |
| refresh_token | 加密存库，**每天 03:00 巡检**，剩余有效期 < 7 天时自动续期 |
| 续期失败 | 立即写 alert_event，飞书私聊运营 + 群里 @负责人，附重新授权链接 |
| 失效兜底 | 账号标记 `status=expired`，采集任务自动暂停，复盘报告显式标注「数据截至 X 日」 |
| 密钥管理 | AES-256-GCM，主密钥放环境变量 / KMS，密文列记录 `key_version` 便于轮换 |

> 抖音 refresh_token 为滚动有效期（续期后重新计时），正常月更一次即可长期持有；具体时效以当时官方文档为准，代码里不硬编码天数，统一从接口返回的 `expires_in` 计算。

### 4.3 多平台凭证矩阵

| 平台 | 授权方式 | 长期可行性 | 备注 |
|---|---|---|---|
| 抖音 | OAuth 授权码 + 代运营/经营授权 | ✅ 高 | 有代运营合作号、经营授权形态，适合我方身份 |
| 快手 | OAuth 授权码 | ✅ 高 | 能力与抖音近似 |
| B站 | OAuth 授权码 | ✅ 高 | 数据类 scope 需申请 |
| 小红书 | 开放平台偏电商交易链路 | ❌ 低 | 笔记/账号经营数据不对普通第三方开放 |
| 视频号 | 微信生态基本不开放 | ❌ 极低 | 只能人工导出或客户本机 RPA |

**工程含义**：`platform` 字段必须做成可扩展枚举，且 `account_auth.auth_mode` 支持 `oauth` / `manual_import` / `local_agent` 三种，避免小红书、视频号客户被架构排除。

## 5. 采集层设计

### 5.1 Adapter 插件接口

每个平台实现同一个接口，新增平台只加一个文件，不动主流程。

```python
class BaseAdapter:
    platform: str                     # "douyin"

    def build_authorize_url(self, state: str) -> str: ...
    def exchange_token(self, code: str) -> TokenBundle: ...
    def refresh_token(self, rt: str) -> TokenBundle: ...

    def fetch_account_daily(self, ctx, date: date) -> list[MetricRow]: ...
    def fetch_contents(self, ctx, since: date, until: date) -> list[ContentRow]: ...
    def fetch_fans_profile(self, ctx, date: date) -> list[MetricRow]: ...  # 不支持则返回 []
    def capability(self) -> set[str]: ...   # 声明本平台能提供哪些 metric_code
```

`capability()` 是核心：**复盘引擎先查能力表，拿不到的指标一律走「缺失」分支，绝不臆造数值。**

### 5.2 调度策略

| 任务 | 频率 | 时间窗 | 说明 |
|---|---|---|---|
| 日指标采集 | 每日 | 06:00–08:00 随机错峰 | 平台 T+1 出数，留足延迟 |
| 作品列表增量 | 每日 | 同上 | 只拉近 7 天有更新的作品 |
| 作品明细回补 | 每 3 天 | 02:00 | 发布 3 天内的作品指标爬坡快，需反复刷新 |
| 粉丝画像 | 每周 | 周一 04:00 | 变化慢，省配额 |
| 历史回补 | 手动触发 | — | 新签客户补齐近 90 天，用于基线对比 |

调度实现：APScheduler（单机够用）或 系统 cron + 幂等脚本。**不建议一开始上分布式调度**，10–50 个账号单机完全扛得住。

### 5.3 限流与容错

- 令牌桶限流：按平台配额配置，例如抖音单 app 取保守值，全局串行 + 100ms 间隔起步
- 重试：指数退避 3 次（1s / 4s / 16s），4xx 不重试（除 429）
- 熔断：单账号连续失败 5 次 → 该账号暂停 6 小时 + 告警；单平台失败率 > 30% → 全平台暂停 + 强告警
- 原始报文：所有成功响应原文落 `collect_raw`（保留 30 天，可按需延长），出问题可离线重放，不用重新拉

### 5.4 幂等

所有快照表建 `UNIQUE KEY (account_id, stat_date, metric_code, dim_type, dim_id)`，写入用 `INSERT ... ON DUPLICATE KEY UPDATE`，天然幂等，任意重跑安全。

## 6. 存储设计

### 6.1 库表清单

| 表 | 用途 |
|---|---|
| `account_profile` | 客户与账号档案（谁、哪个平台、处于什么阶段） |
| `account_auth` | 授权凭证（加密）与状态 |
| `auth_event` | 授权审计日志（谁在何时授权/撤销/续期失败） |
| `collect_task` | 采集任务配置（频率、范围、开关） |
| `collect_run_log` | 每次采集执行记录（耗时、条数、错误） |
| `collect_raw` | 原始报文（可选，排查用） |
| `metric_dict` | 指标字典（统一口径的唯一真相源） |
| `metric_snapshot` | 账号级指标长表快照 |
| `content_snapshot` | 作品级快照 |
| `alert_event` | 告警事件 |
| `review_report` | 复盘报告（结构化 JSON + 渲染后 Markdown） |
| `llm_usage` | Token 消耗（对齐母文档公共约束） |

### 6.2 建表 SQL

```sql
-- ============================================================
-- 任务三 · 账号数据复盘 初始化脚本
-- MySQL 8.0+ / utf8mb4
-- ============================================================
CREATE DATABASE IF NOT EXISTS crabot_review
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE crabot_review;

-- ---------- 1. 账号档案 ----------
CREATE TABLE account_profile (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id       VARCHAR(32)  NOT NULL COMMENT '客户ID，多租户隔离键',
  client_name     VARCHAR(64)  NOT NULL COMMENT '客户名称',
  platform        VARCHAR(16)  NOT NULL COMMENT 'douyin/xiaohongshu/wechat_channels/kuaishou/bilibili',
  platform_uid    VARCHAR(64)  NULL     COMMENT '平台侧账号唯一标识（open_id/uid），授权后回填',
  account_name    VARCHAR(128) NOT NULL COMMENT '账号昵称',
  account_handle  VARCHAR(128) NULL     COMMENT '抖音号/小红书号等对外标识',
  category        VARCHAR(64)  NULL     COMMENT '赛道/品类',
  follower_base   INT UNSIGNED NULL     COMMENT '签约时粉丝基数快照，用于阶段判定',
  stage           VARCHAR(16)  NOT NULL DEFAULT 'cold' COMMENT 'cold/growth/mature/decline',
  goal_json       JSON         NULL     COMMENT '客户目标：涨粉/转化/种草，及目标值',
  owner           VARCHAR(64)  NULL     COMMENT '我方对接人',
  status          TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0停用',
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tenant_platform_name (tenant_id, platform, account_name),
  KEY idx_platform_uid (platform, platform_uid),
  KEY idx_tenant (tenant_id)
) ENGINE=InnoDB COMMENT='客户账号档案';

-- ---------- 2. 授权凭证 ----------
CREATE TABLE account_auth (
  id                BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id        BIGINT UNSIGNED NOT NULL,
  platform          VARCHAR(16)  NOT NULL,
  auth_mode         VARCHAR(16)  NOT NULL DEFAULT 'oauth' COMMENT 'oauth/manual_import/local_agent',
  scope             VARCHAR(512) NULL     COMMENT '已授权 scope，逗号分隔，用于能力判定',
  access_token_enc  VARBINARY(2048) NULL   COMMENT 'AES-256-GCM 密文',
  refresh_token_enc VARBINARY(2048) NULL   COMMENT 'AES-256-GCM 密文',
  key_version       SMALLINT     NOT NULL DEFAULT 1,
  access_expire_at  DATETIME     NULL,
  refresh_expire_at DATETIME     NULL,
  last_refresh_at   DATETIME     NULL,
  refresh_fail_cnt  SMALLINT     NOT NULL DEFAULT 0,
  status            VARCHAR(16)  NOT NULL DEFAULT 'active' COMMENT 'active/expired/revoked/error',
  authorized_by     VARCHAR(64)  NULL     COMMENT '操作人',
  authorized_at     DATETIME     NULL,
  remark            VARCHAR(255) NULL,
  created_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_account (account_id),
  KEY idx_status_expire (status, refresh_expire_at)
) ENGINE=InnoDB COMMENT='账号授权凭证，凭证一律密文';

-- ---------- 3. 授权审计 ----------
CREATE TABLE auth_event (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id  BIGINT UNSIGNED NOT NULL,
  event_type  VARCHAR(24) NOT NULL COMMENT 'authorize/refresh/refresh_fail/revoke/expire',
  detail      VARCHAR(512) NULL,
  operator    VARCHAR(64) NULL,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_account_time (account_id, created_at)
) ENGINE=InnoDB COMMENT='授权审计日志';

-- ---------- 4. 采集任务 ----------
CREATE TABLE collect_task (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id   BIGINT UNSIGNED NOT NULL,
  task_type    VARCHAR(24) NOT NULL COMMENT 'daily_metric/content/increment/fans/history',
  cron_expr    VARCHAR(64) NOT NULL DEFAULT '0 0 7 * * ?',
  lookback_day SMALLINT    NOT NULL DEFAULT 1,
  enabled      TINYINT     NOT NULL DEFAULT 1,
  last_run_at  DATETIME    NULL,
  last_status  VARCHAR(16) NULL COMMENT 'success/partial/fail',
  next_run_at  DATETIME    NULL,
  created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_account_type (account_id, task_type),
  KEY idx_next_run (enabled, next_run_at)
) ENGINE=InnoDB COMMENT='采集任务配置';

-- ---------- 5. 采集执行日志 ----------
CREATE TABLE collect_run_log (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  task_id     BIGINT UNSIGNED NOT NULL,
  account_id  BIGINT UNSIGNED NOT NULL,
  run_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  cost_ms     INT UNSIGNED NULL,
  row_count   INT UNSIGNED NULL,
  http_status SMALLINT NULL,
  error_code  VARCHAR(32) NULL,
  error_msg   VARCHAR(512) NULL,
  retry_cnt   TINYINT UNSIGNED NOT NULL DEFAULT 0,
  status      VARCHAR(16) NOT NULL COMMENT 'success/partial/fail',
  PRIMARY KEY (id),
  KEY idx_account_time (account_id, run_at),
  KEY idx_status (status, run_at)
) ENGINE=InnoDB COMMENT='采集执行日志';

-- ---------- 6. 原始报文（可选） ----------
CREATE TABLE collect_raw (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id BIGINT UNSIGNED NOT NULL,
  biz_type   VARCHAR(24) NOT NULL COMMENT 'account_daily/content/fans',
  biz_date   DATE        NULL,
  payload    JSON        NOT NULL,
  created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_account_bizdate (account_id, biz_type, biz_date),
  KEY idx_created (created_at)
) ENGINE=InnoDB COMMENT='原始报文，保留30天后归档/清理';

-- ---------- 7. 指标字典（口径唯一真相源） ----------
CREATE TABLE metric_dict (
  metric_code   VARCHAR(64) NOT NULL COMMENT '统一指标码，如 play_cnt',
  metric_name   VARCHAR(64) NOT NULL COMMENT '展示名，如 播放量',
  metric_group  VARCHAR(24) NOT NULL COMMENT 'traffic/engage/fans/conversion/quality',
  unit          VARCHAR(16) NULL     COMMENT '次/人/百分比/秒',
  agg_type      VARCHAR(16) NOT NULL DEFAULT 'sum' COMMENT 'sum/avg/last/ratio',
  caliber       VARCHAR(512) NULL    COMMENT '口径说明，必须写清楚分子分母/统计窗口',
  is_derived    TINYINT NOT NULL DEFAULT 0 COMMENT '1=由其他指标计算得出',
  platform_map  JSON NULL COMMENT '{"douyin":"statistics.play_count","kuaishou":"..."} 平台字段映射',
  sort_no       SMALLINT NOT NULL DEFAULT 0,
  PRIMARY KEY (metric_code)
) ENGINE=InnoDB COMMENT='指标字典';

-- ---------- 8. 账号级指标快照（长表） ----------
CREATE TABLE metric_snapshot (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id   VARCHAR(32)  NOT NULL,
  account_id  BIGINT UNSIGNED NOT NULL,
  platform    VARCHAR(16)  NOT NULL,
  stat_date   DATE         NOT NULL,
  metric_code VARCHAR(64)  NOT NULL,
  dim_type    VARCHAR(16)  NOT NULL DEFAULT 'account'
              COMMENT 'account/content/fans_gender/fans_age/fans_region/traffic_source',
  dim_id      VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '维度值，如 gender:male、item_id',
  metric_value DECIMAL(20,4) NULL,
  is_missing  TINYINT NOT NULL DEFAULT 0 COMMENT '1=平台不提供/未授权，前端展示为"-"',
  source      VARCHAR(16) NOT NULL DEFAULT 'official' COMMENT 'official/vendor/manual',
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_metric (account_id, stat_date, metric_code, dim_type, dim_id),
  KEY idx_query (tenant_id, account_id, metric_code, stat_date),
  KEY idx_date (stat_date)
) ENGINE=InnoDB COMMENT='指标快照长表，幂等写入';
-- 数据量大时按 stat_date 做 RANGE 分区；注意分区表主键需包含分区列，届时改为 PRIMARY KEY (id, stat_date)

-- ---------- 9. 作品级快照 ----------
CREATE TABLE content_snapshot (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id     BIGINT UNSIGNED NOT NULL,
  platform       VARCHAR(16) NOT NULL,
  item_id        VARCHAR(64) NOT NULL COMMENT '平台作品ID',
  stat_date      DATE NOT NULL,
```

## 7. 复盘 Skill 设计

### 7.1 输入

```json
{
  "tenant_id": "C001",
  "account_name": "客户A-抖音",
  "report_type": "weekly",
  "period": { "start": "2026-01-05", "end": "2026-01-11" }
}
```

### 7.2 处理流程（Skill 内部）

```
1. 解析意图 → 定位 account_id（模糊匹配账号名，多个则反问）
2. 校验数据完备性：
   - metric_snapshot 该周期数据缺失 → 触发一次即时采集（同步等待，带 60s 超时）
   - 仍缺失 → data_quality = none，返回"数据未就绪，已触发补采，请 10 分钟后重试"
3. 计算派生指标 & 环比/同比：
   - 环比 = (本期 - 上期) / 上期
   - 4 周移动平均、波动率（标准差/均值）
4. 规则引擎诊断（确定性，不靠大模型编）
5. LLM 生成叙述性分析与建议（喂结构化结论，不让它算数）
6. 拼装报告 Markdown → 存 review_report → 飞书卡片回推
```

### 7.3 诊断规则（示例，确定性优先）

| 规则码 | 触发条件 | 诊断结论 | 建议方向 |
|---|---|---|---|
| R_FANS_STAG | 粉丝环比 < -1% 连续 2 周 | 账号进入掉粉期 | 检查近 30 天选题偏离度、发布频率 |
| R_PLAY_DROP | 播放环比 < -30% 且 粉丝环比 > -5% | 内容分发受阻，非粉丝问题 | 查完播率、前 3 秒钩子、违规限流自查 |
| R_ENGAGE_LOW | 互动率 < 近 8 周 P25 | 内容吸引力下降 | 对比高互动作品的结构差异 |
| R_UNEVEN | 单条作品贡献 > 60% 播放 | 流量过度依赖单条 | 拆解该条爆款逻辑，横向复制 |
| R_OUTPUT | 周发布 < 3 条 | 更新不足 | 排期补量 |
| R_COMPLETION | 完播率 < 行业基线 | 前段留存差 | 0–3 秒改写、缩减时长 |
| R_FANS_SRC | 推荐流量占比 < 60% | 自然流量池未打开 | 检查标签准确性、互动引导 |

规则配置建议先硬编码在 `rules/` 目录（Git 可管），跑通 3 个月后再考虑落到 `review_rule` 表做后台可配。**不建议一上来做规则配置化，会让调试成本翻倍。**

### 7.4 报告模板（飞书卡片 / Markdown）

```
【客户A · 抖音】周度复盘 2026.01.05–01.11

① 核心指标
   粉丝 12,340（+1.8%）｜播放 86.2万（-12.4%）｜互动率 4.2%（-0.6pt）
② 数据健康度：72 分（较上周 -5）
③ 关键发现（3 条，含证据数字）
   1) 播放下滑主因是 1/7 发布的 2 条作品完播率仅 18%（账号均值 31%）
   2) 本周 1 条作品贡献 63% 播放，流量集中度过高
   3) 粉丝仍在正增长，说明问题在分发效率而非粉丝流失
④ 下周行动建议（可执行、带负责人/截止日）
   · 复刻 12/28 那条 5.2 万播放作品的开头结构（运营 @小李，1/13 前）
   · 单条时长压缩到 25s 以内（编导 @小王，1/14 前）
   · 发布频率提到 4 条/周（排期表已更新）
⑤ 数据说明
   完播率、流量来源：平台未开放该授权范围，本期缺失
```

**第 ⑤ 段必须存在。** 缺数据不掩盖，是这份报告能不能长期被客户信任的关键。

### 7.5 Prompt 设计要点

- 输入只给**已算好的结构化事实**（指标值、环比、触发的规则、证据数字），不让模型做算术
- 强制输出 JSON schema：`{findings:[{code,level,evidence,advice}], actions:[{text,owner,deadline}]}`
- 显式约束：「不得引入输入以外的数字；数据缺失时在对应结论中标注‘数据不足’」
- 防递归：单次复盘最多 1 轮生成 + 1 轮自检修订，禁止自我迭代（对齐母文档「防递归」约束）
- 输出前做数字校验：报告中出现的每个数值必须能在输入中找到或由输入可复算，否则剔除该句

## 9. 异常与告警

| 场景 | 检测 | 动作 | 等级 |
|---|---|---|---|
| refresh_token 7 天内到期 | 每日 03:00 巡检 | 自动续期；失败则私聊运营 + 授权链接 | warn |
| refresh_token 已过期 | 巡检 | 账号停采 + 群里 @负责人 | error |
| 单账号连续 5 次采集失败 | run_log 统计 | 暂停 6 小时 + 告警 | warn |
| 平台整体失败率 > 30% | 聚合 | 全平台暂停 + 强告警 | error |
| 指标突变（环比绝对值 > 300%） | 采集后校验 | 标记疑似异常，不直接出报告 | info |
| 配额余量 < 20% | 平台配额查询 | 降频 + 告警 | warn |

**数据异常检测不能省。** 平台偶发返回 0 或重复计数，不做校验直接出报告会闹笑话。

## 10. 安全与合规

| 项 | 要求 |
|---|---|
| 凭证 | AES-256-GCM 加密，密钥不进代码库；日志全链路脱敏（正则过滤 `access_token=`） |
| 授权留痕 | 每次授权/撤销写 `auth_event`，保留 ≥ 2 年 |
| 客户授权书 | 签约时补一份《数据授权与使用告知书》，明确采集范围、用途、存储期限、撤销方式 |
| 数据最小化 | 只采复盘必需指标，不采集评论正文中的个人信息（如涉及需单独评估） |
| 权限隔离 | `tenant_id` 强制校验，任何跨租户查询在 DAO 层拦截 |
| 出境 | 不涉及（均境内平台） |
| 员工访问 | 后台查看客户数据需二次鉴权 + 操作日志 |

## 12. 验收标准

| 编号 | 验收项 | 判定标准 |
|---|---|---|
| A1 | 授权成功率 | 新账号首次授权成功率 ≥ 95%（人工操作导致的中断除外） |
| A2 | 续期稳定性 | 连续 30 天无因续期失败导致的停采 |
| A3 | 授权失效告警 | token 失效后 ≤ 24 小时触达负责人 |
| A4 | 数据延迟 | 单账号日指标 T+1 08:00 前可查（≥ 95% 天数达标） |
| A5 | 数据准确性 | 随机抽 10 个账号 × 10 个指标，与后台人工读数误差 = 0（非估算指标） |
| A6 | 幂等性 | 同一日期重跑 3 次，数据完全一致 |
| A7 | 报告完整性 | 报告必含核心指标、发现、建议、数据说明四段，缺失字段显式标注 |
| A8 | 数字可追溯 | 报告中任一数值可定位到 metric_snapshot 记录 |
| A9 | 单次复盘耗时 | 查库路径 P95 < 15 秒；含即时补采 < 60 秒 |
| A10 | Token 统计 | 每次 LLM 调用写入 llm_usage，覆盖率 100% |

## 15. 与母文档的差异说明

| 母文档原文 | 本方案改为 | 理由 |
|---|---|---|
| 4.2-1「Agent 保持和客户账号后台的长期连接」 | 「客户一次授权 + 采集服务定时拉取 + 凭证滚动续期」 | Agent 无常驻进程；平台后台无可长连协议 |
